### Ambiguities to clarify with @SWvheerden before coding

Each item has a working interpretation; do not block coding on them unless the maintainer pushes back during review.

1. **Mode 2 signing approach.** SWvheerden's 2026-05-22 comment explicitly leaves the signing path open ("you can do signing like Tari Universe or you can call the signing application. … I am keeping this vagueish on purpose"). **Working interpretation:** a *signing-only* helper (calling `sign_locked_transaction` in-process) is acceptable; spawning a full `minotari_console_wallet` is not. Document our choice in DESIGN.md and PR body so the maintainer can correct us if wrong.
2. **"Instructions are clear and complete" (AC §4) is subjective.** Question to post on the issue if doubt remains pre-submission: "Should the run instructions be considered passing if they reproduce the harness on a single documented OS (e.g. Ubuntu 22.04), or must they cover macOS/Windows as well?"
3. **S5 arm coverage for Payment Processor mode.** Issue says "batch arm for payment processor; individual arm for new wallet and old wallet". Does Payment Processor mode also need an Individual-arm run for direct multiplier computation? **Working interpretation:** compute multiplier within PP mode by also running its Individual arm; record but mark as "context".
4. **S6 expected-history count.** Issue says "≈ 127 txs (S1) + S4 txs + 110 txs (S5) ≈ 250+". S4 tx count depends on `concurrent_batches` and per-batch success. **Working interpretation:** record only, no assertion.
5. **Generous-but-bounded timeouts.** Principle says "Timeouts should be generous". Only `S4_T_budget=15min` is numeric. **Working interpretation:** no global timeout; per-tx confirmation has a sensible default we record in config.
6. **`fee_rate` "pinned" value.** Config table says `fee_rate` is "pinned" with no number. **Working interpretation:** pick a fee_rate, document it in the baseline profile, treat the value itself as a recorded parameter — the AC is satisfied by recording, not by matching a specific number.

### Out of scope (issue is silent or excludes)

- **Mainnet runs.** Issue specifies Esmeralda testnet only.
- **Wallet funding step.** Explicitly: "the funding step is not part of the measurement." Funding tx fees/timings excluded.
- **CI green status.** Issue does not require CI; competitor PRs added it on their own initiative. Useful but not an AC.
- **Comparison against historical baselines.** Issue requires a baseline profile, not deltas vs. prior runs. Future-run automation is not in scope.
- **Performance assertions / pass-fail thresholds on metrics.** Result profile records numbers; no AC says "scan must complete in < X seconds" or "throughput multiplier must be ≥ Y".
- **Recovery, fix, or improvement of any wallet pain observed.** Principle: harness *measures*. Filing bugs against the wallets is out of scope.
- **Cross-machine reproducibility guarantees.** AC requires the harness be runnable; not identical numbers across machines.
- **Multi-OS support.** Issue doesn't specify; default to one documented OS (likely Linux).
- **Long-term scheduling / nightly runs / dashboards.** Single committed baseline, not a continuous benchmark service.
- **Custom protobuf vendoring or fork maintenance.** Not asked for — depend on upstream `minotari_app_grpc` at a pinned ref instead (see Context §Competitor lessons).
- **Retry / backoff / partitioning / throttling logic.** Explicitly prohibited (AC-30/31/32).
- **Sweep-back / cleanup of funds.** Issue does not require returning funds to a faucet.

**Mode 2 pipeline (verbatim from PR #99's `wallet_benchmark.rs`, paraphrased):**

1. `minotari create-unsigned-transaction --database-path <db> --password <pw> --account-name default --recipient <address:amount> --output-file <out.json>` (subprocess, blocking).
2. Parse `out.json` into `PrepareOneSidedTransactionForSigningResult` via `TransactionResult::from_json`.
3. `sign_locked_transaction(&key_manager, consensus_constants.clone(), LocalNet, unsigned_tx)` — in-process, returns `SignedOneSidedTransactionResult` containing a `Transaction`.
4. POST to `{base_url}/json_rpc` (JSON-RPC 2.0): `{"jsonrpc":"2.0","id":"1","method":"submit_transaction","params":{"transaction":<tx>}}` via `reqwest`.
5. Response shape: `{"result":{"accepted":bool,"rejection_reason":"None|Orphan|FeeTooLow|TimeLocked|ValidationFailed|AlreadyMined","is_synced":bool,"details":Option<String>},"error":null,"id":"1"}` — confirmed in `tari:applications/minotari_node/src/http/handler/json_rpc/submit_transaction.rs`.

### Competitor lessons (technical)

From `gh pr view 3 -R tari-project/wallet-benchmarks --json files,body` and `gh pr view 4`, plus gemini's review comments. Complements `analysis/COMPETITION.md` (focus there: PR shape; focus here: technical traps to pre-empt):

1. **Don't vendor protos.** PR #4 copies `wallet.proto` (2773 lines) + 4 others into `harness/proto/` — 3,400+ lines of bit-rot. Right move: `minotari_app_grpc = "5.3.1-pre.3", default-features = false`. The published crate has tonic-generated client code already. `minotari_payment_processor` pins this same pattern (`766f80ccc20596413ee208311750c11e02a2841d` git rev of `tari`).
2. **Pinning `minotari-cli` requires a git rev, not a published version.** PR #3's `minotari = { git = "https://github.com/tari-project/minotari-cli.git", branch = "main" }` is wrong twice: (a) branch-tracking is non-reproducible (and the result-profile MUST record exact commits), (b) `minotari-cli`'s schema migrates actively (#124 added migration 00031 the day before the bounty filed). Pin a specific commit; surface that hash in the result profile.
3. **Get the base-node HTTP port right.** PR #3 hardcoded `base_node_http → 18143`. Correct is **9005** for Esmeralda (or HTTPS via `https://rpc.esmeralda.tari.com`). Source: `tari:common/src/configuration/bootstrap.rs::wallet_http_service_default_port`.
4. **The "view-only" excuse is wrong.** Both competitors fell back to gRPC for Mode 2 signing. SWvheerden's reply refutes this: the offline path is `tari_transaction_components::offline_signing::sign_locked_transaction` (`Network::LocalNet` for local cucumber, `Network::Esmeralda` for live). PR #99 demonstrates it end-to-end. **Mode 2 done right is the differentiator.**
5. **`env!("CARGO_MANIFEST_DIR")` makes binaries non-portable.** PR #4's `harness/src/config.rs` does this for the config path — gemini flagged it, never fixed. The harness binary must accept config path as a CLI flag.
6. **Process-management race conditions.** PR #4's `old_wallet.rs` (255 lines) has resource leaks and races flagged by gemini around `minotari_console_wallet` spawn/wait/teardown. Required lifecycle: spawn → poll gRPC `GetState` until `is_synced == true` or `scanned_height == tip_height` → run tests → SIGTERM with timeout → SIGKILL fallback → wait on PID. Don't sleep-then-assume.
7. **Stubs in shipped scenarios are a credibility-killer.** PR #3 has `todo!()` in B0 across two of three modes (acknowledged in author's reply to gemini). The "Harness Measures" principle means: a stubbed scenario is worse than an absent scenario — maintainer cannot tell what's measured vs. hand-waved.
8. **Cucumber is the maintainer's established pattern.** PR #99 shows `@benchmark` tag, excluded from default CI. If the harness wants in-tree adoption later, mirroring PR #99 (single feature per benchmark group, step-defs in Rust) is the path of least resistance. The bounty's repo is a fresh fork — no existing convention to inherit — but cucumber wins on maintainer-mirror grounds.
9. **Neither competitor committed a real baseline profile.** PR #3 explicitly defers it; PR #4 commits a 1-line stub. The AC says *"A baseline result profile is committed alongside the harness code"* — this is the single most uniquely-determining AC item.
10. **Edition 2024 vs 2021.** PR #3 sets `edition = "2024"`, PR #4 sets `edition = "2021"`. Tari workspace uses `edition = "2021"`. Mirror the maintainer's repo.

## Risk Surface

### Tier: TIER-2 (API contact only)

The harness calls into wallet/signing APIs (`minotari_console_wallet` gRPC, `minotari` crate including `sign_locked_transaction`) and handles live testnet seed material, but does not modify any consensus, wallet, bridge, or signing code in any Tari repo. It is API consumer code in a brand-new standalone repo.

### Surface inventory

- **Consensus: no.** No block validation, header validation, PoW, JMT, difficulty, hash-domain-separation, or reorg code is read, written, or forked. Harness queries chain tip and waits for confirmation depth `C_min` via existing base-node RPC — pure read-side API consumption.
- **Wallet: API contact only, no in-tree modification.** Heavy exercise of the wallet surface (scan from genesis/birthday in B0/S2/S3/S6/S7, broadcast in S0/S1/S4/S5, balance reconciliation, AC-24 birthday-rewrite) but every wallet operation routes through the *existing* `minotari` crate API or `minotari_console_wallet` gRPC. **No fork, no vendored wallet code, no path-deps into `tari` / `minotari-cli` source trees.** Depend on published crate versions or pinned git commits, never workspace-merge.
- **Bridge: no.** Zero contact with `wxtm-bridge`, attestations, signature aggregation, cross-chain messaging.
- **Signing: API contact only.** Mode 2 calls `sign_locked_transaction` from the `tari_transaction_components` crate. This is invocation of an existing exported function, **not** a new Schnorr/MuSig/range-proof implementation. The harness must not implement key derivation, seed→key reduction, commitment construction, or any primitive that lives under `*/signing/`, `*/sign.rs`, `*/keys.rs`, or `*/wallet_keys/`. If the architect proposes any of those, the tier escalates to TIER-1 and arch-security must sign off.

### arch-security required for Phase 1b?

**No — but with a hard conditional re-flag.** Per CLAUDE.md §Risk-Surface Pre-Flight Gate, arch-security is mandatory when changes touch consensus/wallet/bridge/signing *code*. The gate is about modification, not invocation. The bounty as scoped requires neither — diff is process lifecycle, gRPC client wiring, scenario state machines, structured result emission. None of those are risk-surface code. Phase 1b proceeds with `arch-system` + `arch-test` only. **However**, if during Phase 1b the architect proposes any of the patterns in "Items to revisit" below, spawn `arch-security` immediately and re-gate.

### Guardrails the design must include (even at TIER-NONE)

- **Mainnet-protection guard.** Harness must refuse to run if `network != esmeralda` (hard-coded allowlist, not a warning). Base-node URL and wallet network flag must both be cross-checked at startup; if either says mainnet or they disagree, exit non-zero before any wallet process spawns. This is the single biggest footgun — S1's 127 txs + S4's up to 128 concurrent broadcasts + S5's 110 against mainnet would burn real XTM and embarrass the bounty.
- **Seed handling: never log, never serialize to result profile, never commit.** Test seed phrases loaded from env vars (`HARNESS_SEED_OLD_WALLET`, etc.) or an external file path passed via CLI, never embedded in `config.toml`. Per CLAUDE.md §Secrets, treat testnet seeds as production secrets in the source repo even if funds are valueless — both because the convention must survive any future copy-paste into a mainnet harness and because the maintainer will reject a PR shipping seeds in the diff.
- **`.gitignore` from commit 1.** Must include: `.env`, `.env.*`, `*.seed`, `seeds/`, `wallets/`, `*.tari/`, wallet data directories the harness creates, any `~/.tari/` or `~/.local/share/tari/` paths if pointed there, faucet API tokens, gRPC TLS client keys.
- **Result profile redaction.** Define an explicit allowlist of recorded fields: pinned versions, hardware specs, per-scenario metrics, fee rate, `A_fund`, `C_min`, etc. Define an explicit denylist: seed phrases, view keys, spend keys, wallet passphrases, raw signed transaction blobs, gRPC bearer tokens, faucet credentials, `$HOME` paths that disclose username. Denylist gets unit-tested ("`serde_json::to_string(&profile)` must not contain any of these substrings").
- **Wallet data directory scoping.** Per-scenario wipes confined to harness-owned tempdirs (e.g. `target/harness-data/<run-id>/`), never a user's real `~/.tari/`. Wipe routine refuses paths it didn't create.
- **Process lifecycle hygiene.** Spawned `minotari_console_wallet` processes killed on harness exit including panic + Ctrl-C paths; a zombie wallet process holding a wallet file open across scenarios produces silently wrong results and could leak the wallet password into a stale gRPC port.
- **Faucet credentials and base-node URLs.** Treat as secrets even if "public"; load from env, never commit. Record only the *network identifier* (esmeralda) and a redacted host in the result profile.
- **Transaction broadcasting auditability.** Log every txid the harness broadcasts to a per-run file (gitignored). If something goes wrong on testnet, that log is the only way to reason about state without re-scanning.

### Items to revisit when the design is drafted

- **If the architect proposes a custom seed-manager, key-derivation helper, or any code that reduces a mnemonic to a spend/view key locally inside the harness** (rather than handing the seed to `minotari_console_wallet --recover` or to the existing `minotari` crate's seed-loading API) → escalate to TIER-1, spawn `arch-security`, require `DESIGN.md §Security` signoff before `swe-impl`.
- **If Mode 2's "no external wallet process" requirement forces the architect to call lower-level primitives in the `minotari` crate** (commitment construction, range proof generation, Schnorr signing of inputs) **rather than the single exported `sign_locked_transaction` entry point** → re-flag. Calling one documented public function is API contact; reaching into private signing internals via path-dep or vendored fork is not.
- **If the architect chooses to depend on `tari` or `minotari-cli` via path-dep or git submodule rather than published crate versions or pinned external git revs** → re-flag — this opens the door to local diffs that would silently modify wallet/signing code and bypass this gate.
- **If the architect proposes any retry/backoff/UTXO-pre-partitioning to "stabilize" S4** → not a security risk per se, but an AC failure mode (AC-30/31/32) arch-system should kill on sight.
- **Timing side-channel on a real (non-test) wallet:** harness records construction time, broadcast→mempool time, broadcast→confirmed time. Against testnet, fine — keys are disposable, figures are the whole point. If the architect ever proposes running the same harness against a wallet holding mainnet funds (e.g. "use a maintainer's existing wallet to skip the funding step"), timing data becomes a potential side-channel disclosure. **Disallow in design:** harness only runs against freshly-generated testnet wallets.
